  `docs/work-packages/20260825_cap_runtime_deploy_hardening/`
- **Reviewer**: Codex secondary QA reviewer (`cap_qa_review`)
- **Date**: 2026-08-25

- **Scope**: CAP Node tests, CAP image validation, production Compose mounts,

- **Implementation changes made by this review**: none

## Verdict

- **Gate status**: `fail`
- **Unresolved findings**: Critical 0; High 4; Medium 3; Low 0
- **Implementation recommendation**: hold until QA-01 through QA-04 are
  dispositioned in the ExecPlan and tracker
- **Production recommendation**: keep the current wepp1 containment; do not
  rely on the existing automated gates for another CAP recreation

The package has the right user outcome and names the original EACCES
signatures, but the current tests can still report success for the exact
production failure. The durable repair needs a mandatory host-Docker runtime
gate and executable deploy-script tests. Static string assertions, a tmpfs
mount, and the current shallow health endpoint cannot establish production
readiness.

## Current Coverage and Direct Evidence

### Existing automated coverage

- `services/cap/config.test.js` has three tests for challenge-count and
  challenge-difficulty parsing. It does not start CAP or exercise its secret or
  persistent data mounts.
- `tests/weppcloud/test_auth_cap_captcha.py` and
  `tests/weppcloud/routes/test_cap_verify.py` cover Flask form and verification
  behavior with the CAP network boundary replaced. They cannot reproduce a
  container filesystem permission failure.
- `docker/validate-aux-image-contract.sh` starts CAP with the secret in the
  `CAP_SECRET` environment variable and mounts `/var/lib/cap` as tmpfs. It does
  not use `CAP_SECRET_FILE`, a mode-0600 bind-mounted Compose secret, or a named
  volume.
- `tests/docker/unit/test_rq_worker_startup_contract.py` checks the production
  deploy script by searching for literal strings. It does not execute any
  deploy mode, command ordering, failure branch, rollback, or cleanup branch.
- `tests/docker/test_canary_smoke_contract.py` provides a useful Compose render
  precedent, but its Docker Compose case skips in the normal `wctl run-pytest`
  container because the Compose plugin is unavailable there. A CAP release
  gate must not silently skip at the required mount boundary.

### Reproduction evidence gathered by this review

The following checks used only uniquely named disposable containers and
volumes, synthetic CAP values, and bounded logs. Cleanup removed every
disposable Docker resource.

1. The current release-check image runs as `10001:10001`.
2. A bind-mounted host secret owned by UID/GID `1000:1000` with mode `0600`
   remained `1000:1000/0600` inside the container and was not readable by UID
   `10001`.
3. Starting CAP with that `CAP_SECRET_FILE` exited 1 with the original
   `EACCES: permission denied, open '/run/secrets/cap_secret'` signature.
4. A genuinely new empty named volume inherited `/var/lib/cap` ownership
   `10001:10001` from the image and was writable. Docker's empty-volume copy-up
   behavior therefore makes this state different from a populated legacy
   volume.
5. A populated named volume whose directory and `tokensList.json` were
   `0:0`, with the ledger mode `0600`, was neither readable nor writable by
   CAP.
6. With a readable synthetic secret and that unwritable populated volume, CAP
   remained running and `GET /cap/health` returned HTTP 200. Its bounded logs
   reported that the tokens file could not be loaded or written and that empty
   in-memory state was being used.
7. Despite evidence 2 through 6, this command passed:

       docker/validate-aux-image-contract.sh cap wepppy-cap:release-check ''
       cap image contract: PASS

This is not a theoretical coverage concern. It is a demonstrated false-green
gate for both production resource classes.

## Severity-Ranked Findings

### QA-01 - High - The existing CAP image gate bypasses both production mounts

`docker/validate-aux-image-contract.sh` replaces the file secret with
`CAP_SECRET` and the named volume with a writable tmpfs. The test therefore
passes while the same image cannot read the production-style secret or use a
populated legacy volume. The current Node and Flask tests do not close this
gap.

Required disposition:

- Add one mandatory host-Docker contract harness that is shared by local
  validation and the CAP build/deployment gate.
- Mount a real mode-0600 file at `/run/secrets/cap_secret` and a real Docker
  named volume at `/var/lib/cap`.
- Run the image under its configured `10001:10001` identity; do not override
  the user in the success path.
- Cover no-ACL failure, UID-specific access success, newly replaced secret
  inode, fresh volume, empty legacy volume, populated root-owned volume, and
  already migrated volume.
- Make this host-Docker gate mandatory. Capability absence must fail the CAP
  release/deploy job with an actionable prerequisite error, not skip.

Status: **Open**.

### QA-02 - High - HTTP 200 does not prove CAP persistence readiness

`services/cap/server.js` returns static success from `/cap/health`. The pinned
CAP dependency starts token loading asynchronously and catches load/write
failures, falling back to empty in-memory state. Direct reproduction returned
HTTP 200 with a root-owned unreadable/unwritable ledger. A deploy test that
only adds the planned public health URL will still miss the second incident
failure.

Required disposition:

- Add a deterministic startup/readiness contract that prevents acceptance
  when the mounted ledger is unreadable, unwritable, malformed, or the wrong
  resource type.
- Test the exact state where the directory exists and the root-owned
  `tokensList.json` is mode `0600`; this must not listen as ready or return 200.
- Retain a separate HTTP liveness check only if readiness has already proven
  the data boundary.
- Exercise a complete challenge, redeem, and siteverify sequence after
  readiness so a shallow route cannot satisfy acceptance.

This finding is the QA counterpart of correctness finding COR-01.

Status: **Open**.

### QA-03 - High - Deploy behavior is not executable-testable and the service set is ambiguous

The only current deploy-script tests assert that selected text occurs in a
roughly 700-line shell script. Dead code, checks in the wrong order, an
incorrect service set, or an unconditional success footer can all satisfy
those tests. In addition, `BUILD_SERVICES` is not the set recreated by a full
`down` plus `up -d`, while `docker compose config --services` can include
profile-only services that a default `up` does not start.

Required disposition:

- Name separate arrays/contracts for build targets, services intentionally
  recreated by the selected mode, and services expected to be running.
- Add an executable fake-command harness that runs the real deploy script and
  records every `wctl`, `docker`, `curl`, and cleanup invocation.
- Prove full wepp1, targeted web, wepp2 worker, and wepp3 fork/archive modes
  independently.
- In full mode, fail on CAP `restarting`, `exited`, or failed readiness and on
  any other expected replacement that is not stable.
- In targeted mode, prove CAP is not built, preflighted, stopped, recreated,
  health-claimed, or included in rollback.
- Assert the success footer and prune occur only after every required check.

This finding extends correctness finding COR-04 with the required executable
test seam.

Status: **Open**.

### QA-04 - High - Fail-closed ordering and rollback cleanup are not yet provable

The ExecPlan requires rollback rehearsal but does not define a testable
known-good image reference, the exact point at which CAP resource validation
must run, or separate recovery behavior for pre-stop, partially migrated, and
post-start failures. The current deploy script can stop the whole stack before
detecting CAP failure, and its success path later prunes unused images. A
nonzero exit is not fail-closed if production remains on the broken candidate
or the previous local image has disappeared.

Required disposition:

- Build the candidate and validate its runtime identity/resources before the
  first `down` or recreation command. A failed preflight must leave the
  currently serving CAP container and ledger untouched.
- Record a stable host-local reference to the currently running CAP image
  before build/recreation. This is a Docker Compose host rollback; it must not
  introduce a registry or Kubernetes workflow.
- On post-start readiness failure, restore the known-good CAP service and
  prove it serves CAP before returning nonzero.
- Do not prune the known-good image until the rollback observation gate has
  passed.
- Distinguish cleanup for interrupted partial migration from rollback after a
  completed migration. In both cases preserve ledger bytes, remove disposable
  test resources, and leave no broad permission change.
- Add a test where rollback itself fails. The script must emit a loud bounded
  error, never print `Deployment complete`, and retain recovery artifacts.

This finding is the QA counterpart of correctness finding COR-02.

Status: **Open**.

### QA-05 - Medium - The legacy-data oracle can pass without proving reuse

The ExecPlan currently allows the legacy ledger to be "byte-for-byte or
semantically intact" and proposes a checksum or sentinel plus a later
challenge/redeem. Those are not equivalent. CAP can leave old bytes on disk,
fall back to empty in-memory state, and successfully create a new token after
permissions are repaired.

Required disposition:

- Use a syntactically valid ledger containing an unexpired verification token
  generated from a known synthetic test token.
- Prove the file digest is identical immediately after permission migration
  and before CAP is started.
- After restart, call siteverify with that exact pre-migration token and expect
  one success, then verify the expected ledger mutation is persisted.
- Keep expired tokens out of the preservation fixture because CAP cleanup may
  legitimately remove them.

Status: **Open**.

### QA-06 - Medium - Named-volume states need distinct, real Docker fixtures

The plan's orientation says a mounted named volume hides image ownership. That
is true for a populated legacy volume, but Docker copied the image directory's
`10001:10001` metadata into a new empty volume during this review. A bind mount
or a pre-created host directory will not reliably reproduce that behavior.

Required disposition:

- Test an absent/new named volume, a preexisting empty root-owned named
  volume, a populated root-owned named volume, and a populated canonical named
  volume separately.
- Use Docker named volumes, not `tmp_path` bind directories, for those cases.
- Record the copy-up observation in the ExecPlan so implementation does not
  add unnecessary mutation to already valid fresh state.

Status: **Open**.

### QA-07 - Medium - Failure-injection cleanup needs positive assertions

The ExecPlan requires a cleanup trap, but acceptance does not assert that the
trap ran after every failure point. Cleanup regressions can leave a rehearsal
secret unreadable, a ledger root-owned, CAP stopped, or disposable resources
attached.

Required disposition:

- Inject an interrupt/failure after each state mutation and after candidate
  startup.
- Assert exact post-case secret mode/ACL, volume UID/GID/mode, ledger digest,
  serving image, container state, and absence of test containers/volumes.
- Never use an existing production-named resource for automated boundary
  tests. Forest failure injection must resolve and verify the exact CAP-scoped
  production resource before mutation.

Status: **Open**.

## Required Executable Test Matrix

The following matrix is the minimum QA contract. Test names are prescriptive
so results can be cited without interpreting a broad suite. Equivalent file
placement is acceptable only if the commands remain deterministic and the
host-Docker gate cannot skip.

### Gate A - Fast code and Compose contract

| ID | Test | Command | Required assertion |

### Gate B - Mandatory host-Docker CAP runtime contract

Build the exact candidate through the canonical production build first, then
run the contract on the Docker host rather than inside `wctl run-pytest`:

    wctl build --no-cache cap
    docker/validate-cap-runtime-contract.sh wepppy-cap:latest

The runtime contract script must create a unique project/resource prefix,
install a cleanup trap before its first Docker mutation, and refuse any volume
or container name outside that prefix.

| ID | Runtime state | Required observation |
| --- | --- | --- |
| B1 | New named volume, readable synthetic mode-0600 secret with UID-specific access | CAP runs as `10001:10001`; data root and created ledger are `10001:10001`; challenge/redeem/siteverify succeeds |
| B2 | Preexisting empty root-owned named volume | Docker copy-up/migration result is canonical and the full CAP flow succeeds without data reset warning |
| B3 | Populated root-owned directory and root-owned mode-0600 valid ledger before repair | Candidate readiness fails with a bounded CAP-data error; public health cannot be accepted; digest is unchanged |
| B4 | B3 after the ratified migration | Directory/ledger contract is canonical; pre-migration token siteverify succeeds once; the resulting ledger mutation persists |
| B5 | Canonical populated volume | Migration is a no-op; digest and metadata are unchanged before startup; existing token remains valid |
| B6 | Migration run twice | Second run exits 0 and changes neither content, ownership, mode, ACL, nor unrelated entries |
| B7 | Mode-0600 bind secret without UID `10001` access | CAP exits nonzero with the secret path and identity only; no secret content appears in stdout/stderr |
| B8 | Same secret with UID-specific read access | CAP reads it; host base mode remains `0600`; group/other read remain absent |
| B9 | Secret replaced by a new mode-0600 inode | Preflight reapplies/verifies only the required UID access before CAP recreation; the old secret value is never logged |
| B10 | Canonical directory with root-owned mode-0600 ledger | Readiness fails before listening; this reproduces the data-file EACCES independently of directory ownership |
| B11 | Zero-byte, invalid JSON, wrong-shape JSON, symlink, directory, and FIFO ledger cases | Each fails explicitly without truncating, following, replacing, or changing metadata on the resource |
| B12 | Forced failure after every migration mutation | Cleanup restores the recorded pre-case state and removes every prefixed container/volume |

The script must finish by enumerating its prefix and failing if any matching
container, network, or volume remains.

### Gate D - Forest1 rehearsal and cleanup

Run only after Gates A through C pass. Use the canonical Compose deployment
entry point and the work-package rollout runbook. Each failure-injection case
must capture, then verify restoration of, the serving CAP image ID, CAP restart
count, secret `stat`/value-free ACL, volume directory and ledger metadata,
ledger digest, and an unexpired synthetic verification token.

| ID | Forest1 case | Required observation |
| --- | --- | --- |
| F1 | Known-good full forward deploy | `/cap/health` and the full challenge/redeem/siteverify flow succeed; local login is interactive in Chromium and Safari |
| F2 | Unreadable replaced secret before deploy | Deploy aborts before stack shutdown; old CAP remains serving; cleanup restores exact ACL/mode |
| F3 | Populated root-owned legacy ledger | Automated migration preserves digest before startup and honors the pre-migration token afterwards |

## Regression Risk Summary

1. **False-green readiness** - highest risk. CAP can serve health 200 while its
   token ledger is unusable, reproducing a noninteractive or endlessly
   verifying login CAPTCHA.
2. **Legacy ledger loss or ignored state** - high risk. Checksums plus a newly
   minted token do not prove the old ledger was loaded; an exact pre-migration
   token must survive.
3. **Deployment outage after detection** - high risk. Returning nonzero after
   taking down the known-good service does not protect users; recovery must be
   part of the tested failure contract.
4. **Mode bleed** - high risk. CAP-specific validation or rollback in targeted
   web, wepp2, or wepp3 modes could introduce needless failures or disruption.
5. **Secret-rotation recurrence** - high risk. A UID ACL tied to the old inode
   disappears when the secret is atomically replaced unless the canonical path
   reapplies and verifies it.
6. **Test pollution** - medium risk. Incomplete failure cleanup can leave the
   next rehearsal falsely passing against repaired state or can leave forest1
   broken.
7. **Harness duplication** - medium maintainability risk. The resource checks
   should have one canonical implementation invoked by the deploy script and
   host-Docker tests; copying permission logic into tests will drift again.
