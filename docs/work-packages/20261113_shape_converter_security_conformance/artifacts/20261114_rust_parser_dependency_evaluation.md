# Rust Shapefile Parser Dependency Evaluation

Date: 2026-11-14

Decision: accept `shapefile` 0.9.0 for the service-local
`shape_parser_cli`, subject to the locked dependency graph, executable limits,
adjacent provenance sidecar, and release gates in this work package. This is not
an assertion that all Rust code is memory safe or that the CLI is a second
sandbox.

## Precedent and overlap

The dependency precedent registry contained no prior Shapefile parser
evaluation. WEPPpy's owned Rust components do not parse the Shapefile binary
format. The crate replaces only the hostile-input Fiona/GDAL read path; PyProj,
Shapely, conversion, archive admission, and artifact generation remain owned by
the existing service.

Fiona cannot provide a non-GDAL backend, and Pyogrio also uses GDAL. A new
microservice or an in-process PyO3 binding would add topology or couple parser
failure to the API process without adding format capability. The standalone CLI
is therefore the smallest bounded integration.

## Dependency tax and unsafe surface

`Cargo.lock` resolves 30 packages including the local binary crate. The runtime
graph is small and requires no native Shapefile/GDAL library or separate runtime
environment. All resolved packages declare permissive licenses (MIT,
Apache-2.0, BSD-3-Clause, Unlicense, or Unicode-3.0 combinations).

`cargo audit 0.23.0` loaded 1,509 RustSec advisories and reported no
vulnerabilities for the locked graph. This is a point-in-time gate, not a
substitute for release scanning.

The implementation is not `unsafe`-free:

- WEPPpy owns one documented `unsafe` call to `libc::setrlimit`; it passes a
  fully initialized `rlimit` and fixed resource constants.
- `dbase` uses one bounded pointer loop for whitespace trimming.
- `encoding_rs`, `simdutf8`, and several standard ecosystem transitive crates
  contain unsafe/SIMD optimizations. They remain in the executable's trusted
  computing base.
- `shapefile` contains optional `geo-traits` unsafe methods in source, but that
  feature is not enabled in the resolved graph. The CLI uses the crate's reader
  types directly.

This surface is materially narrower than GDAL's broad native driver stack, but
it does not justify an arbitrary-code-containment claim. Process-group kill,
`RLIMIT_AS`, `RLIMIT_CPU`, `RLIMIT_FSIZE`, `RLIMIT_NOFILE`, input/output quotas,
and outer-container controls remain required.

## Capability and malformed-input evidence

The selected crate reads every Shapefile geometry family needed by the service:
Point, Polyline, Polygon, Multipoint, their M/Z variants, NullShape, and
MultiPatch. The CLI maps them to the preexisting JSON IPC contract and owns a
bounded DBF decoder so Fiona-compatible null dates (`00000000`) remain valid.
The crate release includes allocation/overflow hardening; WEPPpy additionally
checks SHX/DBF record counts, aggregate sidecar bytes, symlinks, finite
coordinates, feature and vertex counts, output bytes, and request-root paths.

Direct Rust tests, Python boundary tests, and real GeoJSON/GeoParquet artifact
readback cover valid Point/Line/Polygon, null geometry/attributes, Z points,
MultiPatch, malformed input, disguised files, and quota exits. Fuzz/property
coverage remains a future hardening opportunity, not an acceptance dependency
for this bounded replacement.

## Representative benchmark

A 50,000-feature EPSG:4326 point dataset with string, integer, and floating DBF
fields was generated by the retained Fiona 1.10.1/GDAL 3.12.4 oracle. Input was
5,550,485 bytes across SHP/SHX/DBF/PRJ/CPG.

On the local x86-64 Docker host used for the production-equivalent image build:

| Path | Wall time | Peak RSS | JSON bytes |
|---|---:|---:|---:|
| Rust release CLI | 0.21 s | 84,096 KiB | 4,861,921 |
| Fiona oracle in retained image | 2.81 s | 144,768 KiB | 5,662,102 |

After removing Fiona's inactive `geometries: null` member, all 50,000
geometries, properties, feature counts, and bounds matched. The JSON size
difference is that intentional normalization. This is acceptance evidence for
the representative vector path, not a general performance claim.

## Provenance and update contract

The release image copies `/usr/local/bin/shape_parser_cli` together with
`/usr/local/bin/shape_parser_cli.json`. Schema
`shape-parser-binary-provenance-v1` binds the executable name, version, SHA-256,
size, ELF build ID/interpreter, source-file manifest and hash, source revision,
Cargo.lock hash, compiler executable/hash/version/target, build command, and
build time. Build and runtime validators fail closed on a missing, malformed, or
mismatched pair; readiness also executes a real fixture through that exact
binary.

The sidecar is integrity/provenance metadata inside the image, not a publisher
signature. Image-digest verification remains the release authenticity boundary.

Reevaluate on any `shapefile`, `dbase`, `encoding_rs`, Rust toolchain, feature,
or resource-limit change. Run locked build/test/clippy, RustSec audit, semantic
artifact parity, exact-image absence checks, and hostile-limit probes before
cutover.
