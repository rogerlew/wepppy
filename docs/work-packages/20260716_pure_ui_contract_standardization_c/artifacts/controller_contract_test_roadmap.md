# Pure UI Controller Contract Test Roadmap

**Status**: Active execution model
**Prepared**: 2026-07-28 UTC
**Scope owner**: GOV-00 Pure UI Controller Contract Standardization

## Goal

Work through the registered controllers one at a time. For each controller:

1. identify its intended field and lifecycle contract;
2. write tests against actual rendered and runtime boundaries;
3. reproduce any mismatch with a failing test;
4. make the smallest compatible patch;
5. run focused and existing broad tests; and
6. retain the regression test before moving to the next controller.

The controller count is backlog inventory. It does not justify a new registry,
planner, change classifier, dependency engine, or CI product.

## Failure Class

WATAR and channel depression smoothing failed at the same seam: the rendered
control did not submit the key/value expected downstream. Existing tests covered
individual layers without proving the user-selected value across:

    rendered id/name/value
      -> browser serialization
      -> route parser
      -> persisted state
      -> reload hydration

The remedy is executable coverage of that seam for each controller, not a
general-purpose contract control plane.

## One-Controller Loop

### 1. Establish intent

Read the current canonical contract and relevant user/operator documentation.
Record only the risk-bearing fields, actions, errors, and completion states. If
intent is absent or conflicting, stop for a bounded decision; do not infer new
behavior from current code.

### 2. Capture observed behavior

Use the actual Jinja template and production controller source. Trace each
risk-bearing value through the existing parser, persistence owner, RQ boundary
when applicable, and reload path. Hand-authored markup is insufficient evidence
for fields generated by templates or macros.

### 3. Add tests before patches

Prefer the cheapest test that crosses the failing seam:

- actual-render assertions for DOM `id`, submitted `name`, option tokens,
  selected/default state, and hidden/disabled/absent behavior;
- focused JavaScript assertions for serialization and hydration;
- focused route/NoDb tests for parsing, persistence, and reload;
- focused RQ tests only when the value or lifecycle reaches a worker.

If no mismatch exists, retain the tests and mark the covered behavior. If a
mismatch exists, prove the test fails for that mismatch before patching when
practical.

### 4. Patch minimally

Change only the confirmed incompatible token, parser, selector, persistence, or
reload path. Preserve public keys, aliases, persisted representations, defaults,
parameterization, authorization, queue wiring, and unrelated shared behavior by
default.

A shared macro/helper change is allowed only when a controller-local repair is
not correct. Before changing it, add regression coverage for the affected
controller and its directly identified consumers. Do not pre-audit every
consumer or build a fan-out engine.

### 5. Validate and move on

Run focused tests first, followed by existing applicable frontend and Python
gates. Rebuild generated controller assets through the canonical builder only
when their source changes. Record the tested revision and remaining gaps, then
close the controller package before starting the next one.

## Tooling Boundary

Tooling exists to reduce repeated test code and mistakes. It must be extracted
from completed controller tests, not designed in advance.

Allowed initial tooling:

- a small assertion helper for actual-rendered field identity and state;
- a small helper for serialized payload comparison;
- existing Jinja/Flask, Jest/jsdom, pytest, controller build, and stale-bundle
  checks; and
- a concise per-controller test matrix used by humans and tests.

Deferred unless measured evidence justifies them:

- machine obligation registries;
- generated documentation indexes;
- source/contract/test manifests;
- base-revision change classifiers;
- shared-consumer dependency graphs;
- no-impact attestations;
- machine-enforced decision ancestry;
- new CI workflows, receipts, recovery, or attestation systems.

Extract a helper only after at least two controller tests repeat the same logic.
Keep helpers stateless and test-only. A helper must make the test shorter and
clearer than direct assertions; otherwise use direct assertions.

## Low-Regression-Risk Rules

- One controller package is active at a time.
- Write or identify the regression test before the production patch.
- Use actual rendered markup for template-defined fields.
- Do not combine cleanup, refactoring, or redesign with mismatch repair.
- Preserve backward-compatible parser and persisted-state behavior unless a
  separately approved decision says otherwise.
- Re-triage security only when production behavior changes a security boundary;
  test-only additions do not inherit a controller's hypothetical maximum risk.
- Require one independent correctness review for a production patch. Require a
  dedicated security review only when the patch changes an attack surface.
- Run the full existing frontend suite after controller JavaScript changes and
  the relevant Python suite after route/NoDb/RQ changes.
- Revert or narrow a shared change when direct-consumer coverage is unavailable.

## Simplicity Budget and Stop-Loss

Until the first five controller packages close:

- use no new machine-readable governance schema;
- add no new CI workflow;
- add at most one small test-helper module per language;
- keep helper implementation smaller than the controller regression tests using
  it; and
- spend no separate package on tooling.

Stop and simplify when:

- two failures are caused by the test tooling rather than product code;
- a cheap deterministic check occurs after a broad test run;
- maintaining metadata takes longer than writing the controller test;
- a controller repair requires more governance files than product/test files;
- tooling needs operator interpretation to decide whether an ordinary change
  passes; or
- tooling expansion is proposed without a measured missed defect or repeated
  test burden.

Crossing a stop-loss requires an explicit operator decision before continuing.

## Measured Value Gate

After five controllers, record:

- mismatches found;
- regressions that fail when each defect is reintroduced;
- focused and broad test runtime;
- helper lines versus controller-test lines;
- false failures caused by tooling; and
- operator time needed per controller.

Continue the same loop if it is finding defects cheaply. Modify tooling only for
measured repetition or misses. Do not reconsider a maintenance gate until the
existing tests demonstrably fail to protect touched controllers.

## Execution Order

Start with DOM-01 WATAR/Ash because it has a known historical mismatch. Then
continue one controller at a time from the reviewed register, adjusting order
only for current incidents or explicit operator priority. Shared packages are
not prerequisites; shared behavior is tested when encountered by a controller.
GOV-01 remains a deferred evaluation, not a gate.

## Completion

The initiative succeeds through accumulated controller regression coverage:
each completed controller has actual-render evidence, downstream
parser/persistence/reload evidence where applicable, a minimal patch for every
confirmed mismatch, and passing existing test gates. It does not require a new
contract platform.
