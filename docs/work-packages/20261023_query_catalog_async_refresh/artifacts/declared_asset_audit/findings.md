# Declared query assets — production and writer audit

November 22, 2026. **Producer-owned declarations are feasible for normal projects and both Omni child types. Parent catalog visibility is the open design decision.** One set of normal project families can describe the child-local datasets. A separate scope resolver must select inherited inputs and map any child keys exposed by the parent. A single recursive root such as `_pups`, `wepp/output` or `export` would both lose that distinction and reintroduce traversal.

This was a read-only audit of code, published catalogs and selected Parquet schemas. Its counts describe retained behavior and source provenance. They do not confer approval to publish or retire a dataset.

## Production evidence

On wepp1/wepp2, 181 catalogs yielded 43,259 entry occurrences. The 12 normal projects came from a reproducibly shuffled sample of pending run locators without an Omni subtree. One conflicting scope identity was skipped. The three Omni parents came from the earlier slow-worker study. We listed both child directories on each parent and read every directly contained nonsymlink child directory's catalog. All 10 scenarios and 156 contrasts had a readable catalog. Every included catalog passed two identical byte reads. Catalogs were read independently, without a fleet-wide atomic snapshot.

### Logical and physical locations diverge

On wepp1, 58 selected Parquet keys covered normal runs, parents, scenarios and contrasts. Passing the stored catalog directly to the planner under the current scope gave 42 successful path/schema checks and 16 permission errors. Applying the existing scope-aware source relocation to the same entries and reading their footers succeeded for all 58. This isolated diagnostic bypassed the mutating freshness barrier and did not exercise an HTTP request. The permission errors are evidence against trusting a stored absolute root, not proof of 16 user-facing failures.

All 14 sampled child climate/watershed bindings resolved to the parent. All 21 sampled child soils, landuse and WEPP bindings resolved inside the child. No contrast catalog had an explicit `fs_path`. One scenario alone had 591 explicit absolute `fs_path` values. In 39 catalogs the root string differed from the sampled directory. Keep the logical key relative to its scope and select the current physical source using the existing authorized resolver. Deriving ownership from `fs_path` presence or keeping a resolved absolute path in a declaration would misclassify real projects. It is a search index, not a count of scientific outputs. ## Representation and adoption decision

Use a **small producer-owned descriptor for a logical dataset family**, expanded for one project scope. Reuse existing filename constants, output-scope helpers and manifest readers. A central index can compose descriptors and validate uniqueness without duplicating paths. Three existing patterns cover the cases observed here:

| Representation | Example | How it stays in sync |
| --- | --- | --- |
| Exact relative key | `landuse/landuse.parquet`; the four Omni aggregate tables | The writer, notification and resolver use the same constant. |
| Bounded path template | `climate/gridmet_observed_{topaz_id}_{start_year}-{end_year}.parquet` | The writer and resolver share the filename function. Bind IDs to the actual run or accepted publication. For old runs without membership evidence, match immediate children of the named folder. |
| Selected path or manifest | Uploaded disturbance map, selected export publication, SWAT run | Resolve the controller-owned selection or current manifest relative to the authorized scope. Declare what constitutes a complete publication and what supersedes it. |

Each descriptor needs an owner, logical key or expansion, applicable scope/conditions, and a way to select the physical source. Reuse the existing access/lifecycle checks for local, child-first and authorized parent inputs. Keep `normal`, `scenario` and `contrast` as execution contexts. Parent aggregate keys belong to the parent; publishing a child dataset as a qualified key in the parent is a separate projection decision. A recursive wildcard over every project or copying absolute `fs_path` values into a static registry defeats these semantics.

**Worked example.** The logical key `landuse/landuse.parquet` can be identical in a normal project, a scenario and contrast 12. Normal landuse publication selects the run-local output. A scenario can override the parent's source. The contrast merge writes a new table under `_pups/omni/contrasts/12/landuse/`; it must win over either input scenario. A parent query for `omni/contrasts.out.parquet` selects the aggregator's output, while a parent query for a qualified child loss table needs an explicitly supported child projection. This requires one normal logical key and scope-aware selection, without three copies of the landuse filename specification.

**Keeping declarations current.** Add a fixed or templated family beside its writer and use the same value for the receipt. Test the writer’s actual final outputs against its descriptor for both enabled and disabled options. For a manifest-backed producer, stage the outputs and publish the complete membership using its existing publication protocol. On deletion or rename, reconcile prior and new membership and preserve the existing identity and race checks. For a child, test a parent update, a local override and removal of that override; a retained child must observe the correct physical source in each case. Scope roots in `QUERY_CATALOG_ROOTS_JSON` locate managed projects on storage. Keep dataset-family declarations independent of those deployment-specific mounts.

**Alternatives.** A central YAML list is easy to review but would duplicate writer naming and require repeated changes for optional outputs. The Feature Export schema is a good precedent for static locators and scope variables, but it describes a consumer subset. A per-run manifest alone has no answer for historical projects, failed writers or a crash between file publication and manifest commit. Use manifests only where the producer already has a coherent published set, and use reconstructible declarations elsewhere. Directory-only registration remains useful for bounding old-run discovery when the membership is dynamic. Exact-key proposals should retain a bounded route to finding newly created and deleted family members after missed notifications.

**Feasibility verdict.** Proceed to a shadow resolver for the source-owned families. Compare normal, child-direct and parent-qualified views separately. First exercise climate, canonical soils/landuse, WEPP interchange and the four parent aggregates. Then add one dynamic upload and one manifest-backed exporter. Replay a project created before declarations, a replaced child, a deleted optional output and a producer that stops between file publication and notification. Diff membership, schema and physical source against the current authorized reader; retain unexplained differences. Include synchronous activation, native collection, access-scope pre-scan and both strict inventories in the comparison. Changing only the async scheduler would leave existing full scans in place. [Activation](../../../../../wepppy/query_engine/activate.py) · [Strict refresh](../../../../../wepppy/query_engine/catalog_refresh.py) · [RQ postprocessing](../../../../../wepppy/rq/wepp_rq_stage_post.py)

Before production adoption, resolve parent visibility using parent-qualified consumer evidence and decide how legacy discovery-only metadata should be served. This audit supports building the resolver. It does not authorize changing the existing catalog, worker configuration or Rocket admission cap.
