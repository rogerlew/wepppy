### VUN-QA-FROZEN-05 - The Batch concurrency regression can pass when its worker crashes

`test_transactional_registration_does_not_clobber_concurrent_template_update()`
uses `time.sleep(0.05)` after a thread sets `attempted`, but never records whether
the thread was actually blocked, completed successfully or raised an exception
(`test_batch_runner_endpoints.py:89-134`). The worker reads
`json.loads(destination.read_text())["marker"]`; the replacement fixture
`tests/data/batch_runner/simple.geojson` has no top-level `marker`. If the
transaction lock regresses and the worker enters early, it raises an uncaught
`KeyError`, terminates, and still satisfies `assert not worker.is_alive()`.
Rollback then restores `{"marker":"old"}`, allowing the remaining assertions
to pass. Pytest's thread warning is not a deterministic failure gate.

This is the primary test offered for the predecessor's concurrent Batch rollback
finding, so the false-green path is Medium rather than Low test style debt.

**Required closure:** coordinate explicit “attempted”, “blocked/retried” and
“completed” events, capture every worker exception into the main thread, and
fail unless the mutation completes after rollback with a unique sentinel. Remove
the scheduling sleep. Prove the worker cannot observe candidate bytes/state while
the receipt callback owns the transaction and that its eventual committed update
survives detached reload.

### VUN-QA-FROZEN-06 - Whole-Batch deletion bypasses the retained-evidence lifecycle

The failure-class remediation covered run deletion and private archive
delete/restore, but missed the established Batch project deletion consumer.
`delete_batch_rq()` recursively removes the complete Batch workspace, including
`resources/vector_upload_attempts`, without acquiring the Batch retention scope,
creating the deterministic rebuild obligation, fsyncing the parent, or rebuilding
global/principal committed totals (`wepppy/rq/batch_rq.py:453-514`). It clears
cache/lock metadata before `shutil.rmtree()` and treats the absent workspace as
complete on retry. The Batch delete tests assert only recursive removal, active-
job refusal and absent-workspace success (`tests/rq/test_batch_rq_delete_batch.py:
22-138`); none contains retained vector evidence or reads the ledger.

The result is conservative accounting leakage rather than byte exposure: users
can delete a Batch project while its retained bytes remain charged indefinitely,
and a retry cannot infer which principal/global amounts require repair. It also
means the validation statement that destructive project deletion is durably
accounted does not cover both run and Batch project identities.

**Required closure:** classify Batch retained evidence before mutation; require
the exact configured filesystem identity/root; acquire global maintenance before
the Batch project scope; persist the same dual rebuild obligation; remove and
fsync durably; exact-root rebuild/read back totals; then clear file and Redis
markers in order. Retry must repair an already absent workspace using the same
globally qualified target. Add real-Redis tests for normal deletion, missing
configuration, partial removal/fsync/rebuild failure, absent-target retry,
unrelated active reservation preservation and exact principal/global totals.
